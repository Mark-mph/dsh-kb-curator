# 知识库体系 —— 冻结契约 v1（Lead 制定，团队共同遵守）

> 本文件是唯一事实来源。teammate 只能按此实现；发现契约有问题**回报 Lead**，不得自行改契约。

## 0. 背景与用户硬约束

用户诉求：持续喂资料 → 分门别类归类并储存记忆 → 随时调用解答 → 联网搜索补齐库外信息 → 自动筛选后**交由用户本人亲自审核批阅**再入库 → 具备自行辨别能力 → 可按用户需求设置优先级，在「不同类别」或「库内信息与网络搜索冲突」时按优先级高低裁定。

硬约束：
1. **只有云端模型（DeepSeek）花钱，其他全部免费**。不得引入任何需要付费的外部服务（不要 Hindsight 云、不要商用嵌入 API、不要 Jev）。
2. `来源等级`：用户提供 > 用户审核通过的联网资料 > 未审核的搜索原文。
3. **Agent 绝不能在用户批准前写入 L2（engram）与 L3（知识页）**。硬约束，无例外。
4. 原文必须留在本地文件（L1），换掉任何检索服务 L1 不动。
5. 冲突无法按规则分出胜负时**不擅自裁定**，标记冲突并送待审队列。
6. **遇矛盾先自行推理正误**（用户新增要求，原话："有些资料会有谬误，请你在以后遇到资料信息矛盾时候自行推理正误，如果你觉得都没问题就按我喂完资料后规定的优先级来，现阶段我还没有规定优先级，请自行推理判断"）：先判正误，判不了的才回落到来源等级 / 优先级 / 置信度。**判错是提案不是终审，用户可推翻**；禁止仅凭「更常见 / 更符合直觉 / 更权威的感觉」判错。见 §5 第 4) 步。
7. **不止存储筛选，还要消化理解并会运用**（用户新增要求，原话："不仅做到存储和筛选，还能通过自行学习，消化理解会运用这些信息资料，为以后我咨询你相关问题打基础"）：见 §9「消化学习层」；消化产物仍须用户批准后才落 L2/L3。

## 1. 三层架构

| 层 | 是什么 | 放在哪 | 谁写 |
|---|---|---|---|
| **L1 原始库** | 资料原文（Markdown），可人眼查看、可版本管理 | `knowledge-base/library/<大类>/<子类>/*.md` | 用户批准后由 agent 落盘 |
| **L2 检索层** | 记忆条目（事实/偏好/决策/事件/技法），进 engram 做混合检索 | engram SQLite（`~/.dsh/engram/user.db`） | 用户批准后 `engram_save` |
| **L3 知识页** | 每个大类一张**消化层 + 综述索引**页（`## <主题>` 下写核心结论 / 原理推导 / 方法步骤 / 适用边界 / 易错点；**不是原文堆放处**） | `knowledge-base/pages/<大类>.md` | 用户批准后更新 |

**关键纪律**：L3 是「综合消化层」。几千份原文**不许**塞进知识页；原文只在 L1，L2 只放提炼后的条目，L3 只放某个大类的消化笔记（五要素）、总览与目录。

## 2. 目录布局（kb-architect 负责创建）

```
knowledge-base/
  kb.config.json                 # root / 默认分类 / 版本
  README.md                      # 中文用户手册（怎么喂料、怎么审核、怎么提问）
  _inbox/                        # L0：用户扔进来的原始资料，尚未处理
  _review/
    queue/                       # 待审提案（一 proposal 一个 .md，含 diff 预览）
    approved/                    # 批准后的提案存档（审核痕迹，可审计）
    rejected/                    # 驳回的提案存档（含驳回理由）
  _system/
    taxonomy.yml                 # 分类体系：大类 → 子类 → 触发关键词
    priority.yml                 # 来源等级 + 优先级 + 置信度规则
    arbitration.md               # 冲突仲裁算法（可执行伪码，逐条对应 §5）
    entry-schema.md              # L1 frontmatter + L2 条目 字段规范
    review-workflow.md           # 五状态审核工作流（对应 §6）
    learning.md                  # 消化学习层：消化产物五要素 + 知识页结构（对应 §9）
    log.jsonl                    # 追加式操作日志（谁在何时改了什么）
  _templates/
    source-note.md               # L1 原文卡模板
    memory-entry.md              # L2 记忆条目模板
    knowledge-page.md            # L3 知识页模板
    review-proposal.md           # 待审提案模板
  library/                       # L1 原始库（见 §1）
    <大类>/<子类>/<yyyy-mm-dd>-<slug>.md
  pages/                         # L3 知识页
    <大类>.md
  kb.ps1                         # 辅助脚本（见 §7）
```

初始大类（写入 `taxonomy.yml`，用户可以随时增改）：
`技术工程` · `产品业务` · `学术研究` · `生活健康` · `财务投资` · `人文社科` · `工具流程` · `未分类`

## 3. L1 原文卡 frontmatter（YAML，字段名固定）

```yaml
id: kb-20261009-0001              # 固定格式 kb-<yyyymmdd>-<4位序号>
title: "标题"
category: 技术工程                 # 必须是 taxonomy.yml 里的大类
subcategory: 前端                  # 可为空
source_type: user_file | user_text | web
source_url: ""                    # web 必填
fetched_at: ""                    # web 必填，ISO8601
added_at: 2026-10-09T12:00:00+08:00
content_hash: "<sha256 原文>"      # 用于去重与版本比对
status: inbox | proposed | approved | rejected | needs_edit | indexed
priority: 3                       # 1-5，5 最高，用户可调
confidence: 0.8                   # 0-1，agent 提案、用户可改
valid_from: ""                    # 时效起点，可空
valid_until: ""                   # 时效终点，空=长期有效
supersedes: []                    # 被本条取代的旧条目 id
tags: []
proposition_key: ""               # 命题键：同一命题的条目共用一个 key，仲裁按它聚类
```

`proposition_key` 是仲裁的核心：形如 `前端/构建工具/vite-默认端口`。同一命题的多条说法靠它分组。

## 4. L2 记忆条目（写入 engram）

- `kind` 用英文：事实→`fact`、偏好→`preference`、决策→`decision`、事件/资料→`episode`、技法流程→`skill`。
  （源码定案：`engram_save` 的 `kind` 收英文；engram 自动排桩到中文房名 `事实厅`/`偏好阁`/`决策堂`/`往事廊`/`技法坊`，**每间满 9 条就分裂出 `决策堂-2`**。因此 **`engram_search` 默认不要带 `room`**，否则会漏掉溢出房间，出现「库里有却搜不到」。）
- engram 每次保存前会做相似度告警：高度相似时必须改用 `engram_update` 归并，不许制造重复条目。
- `scope`：跨项目通用知识与用户偏好用 `user`；项目相关的用 `project`。
- **每条 content 必须带来源标记** `[src:<L1-id>]`，否则视为不合格条目。
- content 建议格式：`<命题>：<结论>。条件：<适用条件>。来源：<L1-id>。`

## 5. 冲突仲裁算法（冻结，逐条实现进 `arbitration.md`，skill 必须严格照做）

**顺序（v1.1 定案：用户新增「正误推理」，作为先于来源等级的独立步骤）**：
```
① 提取冲突 → ② 同领域过滤 → ③ 时效过滤 → ④ 正误推理（新增）→ ⑤ 来源等级投票
→ ⑥ 优先级 → ⑦ 置信度打破平局 → ⑧ 仍打平 → 标记「存在冲突」，不擅自裁定，送待审队列
（另有第 ⑨ 条「库内 vs 联网」细则）
```

输入：问题 q、候选条目集合 C（来自 L2 检索 + 可能的联网搜索）
```
1) 提取冲突：按 (category, subcategory, proposition_key) 聚类；同一命题下的多条不同说法 = 一个冲突组
2) 同领域过滤：只保留 category/subcategory 与 q 相关的条目
3) 时效过滤：valid_until < now 的剔除；valid_from > now 的降级为「未来条目」，不参与裁定但要提示
4) 正误推理（新增，独立于来源等级）——对本组每条冲突声明做**可检验**检查：
   a. 内部自洽：推导 / 计算 / 量纲 / 逻辑
   b. 与公认基准一致：教材、标准定义、学科共识
   c. 与库内其他高置信条目相容
   - 能明确判定为谬误 → verdict=erroneous + 具体理由（推导 / 反例 / 量纲 / 定义冲突）；
     **必须显式告知用户、绝不静默丢弃**，并生成一条待审记录让用户最终确认；被判谬误的条目不得进入 chosen_ids
   - 无法判定（都自洽，或属不同条件 / 版本 / 参数 / 模型假设）→ 进入第 5) 步起的原链条
   - **硬约束：禁止仅凭「更常见 / 更符合直觉 / 更权威的感觉」判错；判错是提案不是终审，用户可推翻**
5) 组内比来源等级 source_rank：user_provided=100 > user_approved_web=60 > unapproved_web=20
6) 同等级比 priority（5 最高）；**用户尚未规定优先级** → agent 自行推理判断，并标注 `by: agent` / `pending_user: true`
7) 仍相同比 confidence（0-1）
8) 仍无法分出胜负 → outcome="conflict"：
   - 不选边；把涉及条目标 conflicted
   - 生成一条冲突提案放入 _review/queue/
   - 回答中显式写出「库内存在冲突说法，已列入待审队列，请你裁定」
9) 库内 vs 联网冲突：库内 user_provided 条目优先；未审核的 web 结果**不参与裁定**，
   只能作为「补充视角」附在答案末尾并标注未审核（此条同样必须先过第 4) 步正误推理）
```
输出：`{chosen_ids, outcome: resolved|conflict, conflict_ids, verdicts, 依据说明}`
```
verdicts 记录第 4) 步结果：`[{id, verdict: sound|erroneous|undecidable, reason, basis}]`
verdict=erroneous 的条目必须同时出现在「给用户的显式告知」与「待审队列」里，不得静默丢弃
```

**答案纪律**：引用任何条目必须写出 `[src:<L1-id>]`，让用户能点回原文核对。

## 6. 审核工作流（五状态 + 两终态）

```
inbox ──agent 提案──> proposed ──用户批准──> approved ──入库──> indexed
                        │                     ▲
                        ├──用户驳回──> rejected
                        └──用户要改──> needs_edit ──agent 改完──> proposed
```

- 每个 `proposed` 提案 = `_review/queue/<id>.md`，内含：原文摘要、建议分类、建议优先级、置信度、**将要写入 engram 的条目正文**、将要更新的知识页 diff。
- 用户批准后 agent 依次做四件事并写入 `_system/log.jsonl`：① L1 落盘 `library/`；② `engram_save`；③ 更新 `pages/<大类>.md`；④ 提案移入 `_review/approved/`。
- 用户驳回：归档到 `_review/rejected/`，L1 丢弃或移入 `_inbox/_rejected/`，并记日志。
- **安全阀**：`proposed` 状态下 agent 不得写 L2/L3；任何绕过均为违规。

## 7. kb.ps1（辅助脚本，kb-architect 实现）

必须支持：
`init` · `add -Path <file> [-Category <c>]` · `list-queue` · `show <id>` ·
`approve <id>` · `reject <id> -Reason "..."` · `search <query>` · `page <大类>` · `log [-Tail N]`

要求：纯 PowerShell，无外部依赖；幂等；出错给出中文可读信息；不得删除已有资料（只移动/追加）。

## 8. 验收标准（verifier 按此逐条核）

1. 目录布局与 §2 完全一致；`taxonomy.yml` / `priority.yml` / `arbitration.md` / `entry-schema.md` / `review-workflow.md` 均存在且与契约一致。
2. `arbitration.md` 的步骤与 §5 一一对应，无遗漏、无自创规则。
3. `kb.ps1` 至少 `init`、`list-queue`、`add`、`approve`、`reject` 五个命令可实际运行（PowerShell 语法校验通过，无解析错误）。
4. `SKILL.md` frontmatter 只有 `name` 与 `description` 两个字段；位于技能安装目录下的 `kb-curator/SKILL.md`。
5. SKILL.md 明确写出：三层架构、五状态审核、**用户未批准不得写 L2/L3**、冲突仲裁顺序（① 提取冲突 → ② 同领域过滤 → ③ 时效过滤 → **④ 正误推理** → ⑤ 来源等级 → ⑥ 优先级 → ⑦ 置信度 → ⑧ 打平即送审，含第 ⑨ 条库内 vs 联网）、引用必须带 `[src:<id>]`、免费约束（禁止 Hindsight 云/付费嵌入）。
6. 不存在任何指向付费服务的默认配置。
7. 用户视角能跑通一次完整往返：喂一份资料 → 看到提案 → 说「批准」→ 条目进库 → 提问能召回并带来源。
8. `_system/learning.md` 存在且给出消化产物五要素与知识页结构；`_templates/knowledge-page.md` 承载该结构，并保留 `{{CATEGORY}}` 占位符与 `<!-- KB:INDEX:BEGIN/END -->` 标记。

## 9. 消化学习层（learning）

> 来源：用户新增要求（原话："不仅做到存储和筛选，还能通过自行学习，消化理解会运用这些信息资料，为以后我咨询你相关问题打基础"）。逐条落地见 `_system/learning.md`。

- **定位**：L2 是「可检索的命题」，L3 是「可运用的理解」。知识页不再只是目录，而是 agent 消化后的**主题笔记**。
- **消化产物五要素**：
  1. 概念与定义（术语 / 符号 / 单位）
  2. 原理与推导链（为什么成立、前提假设）
  3. 方法与步骤（可执行的解题 / 设计流程）
  4. 适用条件与边界（何时可用、何时失效）
  5. 易错点与常见误区 + 与其他知识的联系（前置 / 后继 / 易混对比）
- **知识页 pages/<大类>.md 结构**：`## <主题>` → `### 核心结论` / `### 原理与推导` / `### 方法与步骤` / `### 适用条件与边界` / `### 易错点` / `### 相关条目（entry ids）`。索引行格式不变，追加在文末。
- **两条硬边界**：
  1. **`kb.ps1` 绝不引入 LLM 依赖**（保零成本）。消化由 agent（云端模型，唯一花钱项）完成，脚本只做文件操作。
  2. **消化产物写入 `pages/` 与 L2 仍必须经用户批准**：批准前不得落 `pages/`、`engram`、`library/`（§6 安全阀无例外）。
- **问答时**：先按 §5 仲裁得到 `chosen_ids`，再用知识页的消化内容组织答案（讲解、推导、举例、步骤、适用条件），引用仍必须带 `[src:<L1-id>]`。

## 10. 知识库定位与磁盘契约（追加节，不改写前文）

> 来源：用户新增要求——「存储库建在知识库所在盘的一个固定文件夹、不要存得到处都是；该盘快存满必须提前告知」。
> **本节为追加条款**：前面各章的条款一字不改；前文出现的相对路径（如 §1/§2 的 `knowledge-base/library/...`、`pages/<大类>.md`）一律**相对本节定义的固定根目录解析**。
> 本文档本身（`references/contract.md`，即本技能自带的契约副本）是**设计文档**，位于知识库根之外，不属于知识库数据。

1. **固定根目录**：知识库的根目录**由用户选定**（一个固定的绝对路径）。**引擎自定位**：`kb.ps1` 用 `$PSScriptRoot` 认自己所在的目录，那就是知识库根目录——`kb.config.json` 的 `root` 只是**说明性字段**（出厂为 `"."`），程序不读取它，它**不是权威**。`_inbox/`、`_review/`、`_system/`、`_templates/`、`library/`、`pages/`、`_sources/`、`_staging/` 均为其下相对目录。整个目录搬家（改名 / 换路径 / 换盘）无需改脚本、无需改配置。
   - 用户要求：所有资料**集中**存放在这一个文件夹里，**不放在 agent 工作目录内**，不许散落到别处（包括临时目录、agent 会话目录、仓库工作区）。
2. **大体积中间产物与原始件也要纳入管理**：
   - `_sources/`：用户原始文件的**副本**（二进制，不做加工），用于溯源与重跑 OCR。**出厂为空目录**，随用户投入的资料增长。
   - `_staging/`：OCR / 格式转换的**中间产物，可随时重建**，**不视为知识**（清理它不丢知识，也不入 L1/L2/L3）。典型结构为 `_staging/ocr/{pages,chapters,probe-out}`。
3. **`status` 是只读命令**：`kb.cmd status`（等价 `kb.ps1 status`）只打印根目录、磁盘剩余空间与两条阈值线、待审/已批准/已驳回提案数、L0/L1/L3 计数、日志行数与规范文件齐备情况；**不得写 `_system/log.jsonl`，不得改动任何文件**（验收时可前后比对全库 SHA256）。
4. **收料前磁盘检查是硬前置**：每次 `add` 之前必须检查剩余空间；阈值**可配置**——`kb.config.json` → `storage.warn_free_gb`（默认 20，提醒线）/ `storage.block_free_gb`（默认 5，拒绝线），单位 GB，改完立即生效。
5. **两条线的语义（不得混用）**：
   - 剩余空间 < `warn_free_gb`：**提醒线** —— 打印 `[磁盘告警]` 但**放行**本次收料。
   - 剩余空间 < `block_free_gb`：**拒绝线** —— 打印 `[错误] … 已拒绝本次收料` 并以 **exit 1** 结束，**不落 `_inbox/`**；agent **不得绕过**（不得改用 `-Force`、手动复制、写入临时目录再搬等手段规避），必须先与用户商量腾空间或迁移。
6. **agent 的转告义务**：任何收料或在知识库根下的大批量写入（OCR 产物、批量 L1 落盘、批量整理）之前，**先跑 `kb.cmd status`**；一旦出现 `[磁盘告警]` 或剩余空间接近拒绝线，必须在答复里**显式告知用户**（用户要求：快存满要提前告诉我），不得默默继续。省空间顺序仅为建议：`_staging/`（可重建）→ 已消化完的历史 `_sources/` → `library/` 原文（最后才动，且脚本**永不自动删除**任何资料）。
