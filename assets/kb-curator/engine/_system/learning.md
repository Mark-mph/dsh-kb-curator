# 消化学习层 learning（契约 v1 §9，逐条实现）

> 用户要求（原话）：「不仅做到存储和筛选，还能通过自行学习，消化理解会运用这些信息资料，为以后我咨询你相关问题打基础」。
> **本文件定义「消化产物」长什么样、放在哪、谁来写。** 与 `arbitration.md`（怎么裁定）、`review-workflow.md`（怎么审核）配套。
> 一句话：**L1 是原文，L2 是可检索的命题，L3 是消化后的理解（能拿来讲解、推导、举例、照步骤做）。**

## 0. 三条硬边界（不许破）

1. **`kb.ps1` 绝不引入 LLM 依赖**——脚本只做文件操作（收料、落盘、归档、日志），保持零成本可离线运行。消化由 **agent**（云端模型，全系统唯一花钱项）完成。
2. **消化产物写入 `pages/`（L3）与 `engram`（L2）仍必须经用户批准**。`status: proposed` 时严禁写 L2/L3（契约 §6 安全阀，无例外）。
3. **知识页不是原文堆放处**：不许整段复制原文。可以引用关键句/公式（带 `[src:<L1-id>]`），其余必须是自己消化后的表述。

## 1. 消化产物五要素（核心）

每消化一份/一组资料，产出下面五要素。要素齐不齐，是提案能不能送审的判据之一。

### ① 概念与定义（术语 / 符号 / 单位）
- 写什么：本主题涉及的术语、符号、单位、变量含义；同名不同义的歧义点。
- 判据：**读者只靠这一节就能正确读懂后面的公式与步骤**。
- 例子：`R(s)` 表示参考输入的拉普拉斯变换；`K` 为开环增益，无量纲。

### ② 原理与推导链（为什么成立、前提假设）
- 写什么：从已知条件到结论的推导步骤，或「为什么这样设计」的因果链；明确列出**前提假设**。
- 判据：**每一步都能被独立检验**（代数、量纲、逻辑）；跳步要标注「此处略去标准推导，见 `[src:<id>]`」。
- 反面例子：只写「因此可得 X」而不说凭什么——不算消化。

### ③ 方法与步骤（可执行的解题 / 设计流程）
- 写什么：遇到这类问题**先做什么、再做什么**，编号步骤 + 每步的输入/输出 + 一个最小可算例子。
- 判据：**照抄步骤就能解一道题/做完一次设计**，不需要回头翻原文。
- 例子：
  1. 列写系统微分方程 → 2. 取拉普拉斯变换（零初始条件）→ 3. 求传递函数 → 4. 代入参数算稳态误差。

### ④ 适用条件与边界（何时可用、何时失效）
- 写什么：成立条件、被忽略的效应（非线性、时变、饱和、噪声）、失效场景、与其他模型的适用分界。
- 判据：**能一句话回答「这个结论什么时候不能用」**。
- 例子：二阶近似只在阻尼比 0<ζ<1 且忽略高阶极点时成立；`ζ→0` 时超调量公式失效。

### ⑤ 易错点与常见误区 + 与其他知识的联系
- 易错点：符号错、量纲错、条件漏看、公式套错、单位混用、把充分条件当必要条件。
- 联系：**前置**（要先会什么）、**后继**（接下来学什么）、**易混对比**（跟哪个概念长得像但不一样，差在哪）。
- 判据：**读者踩坑前就被提醒过**；联系项用 `[src:<id>]` 指到库内已有条目/主题。

> 五要素**不必强行五等分**：短资料可以把 ①②合并、③④合并，但**一个都不许缺**，缺的那项要显式写「待补」。

## 2. 知识页结构（L3 `pages/<大类>.md`）

```
# <大类> · 知识页
## 本类综述                       ← 3-8 句总览：主要命题、已形成的共识、存在的分歧
## <主题>                         ← 一个主题一节；主题 = 子类/命题簇，不是资料条目
### 核心结论                      ← 可以直接拿去回答的结论（可多条，每条带 [src:<id>]）
### 原理与推导                    ← 要素 ②
### 方法与步骤                    ← 要素 ③
### 适用条件与边界                ← 要素 ④
### 易错点                        ← 要素 ⑤（含与其他知识的联系）
### 相关条目（entry ids）         ← 支撑本主题的 L1 id 列表，如 kb-20261009-0001
## 待裁定冲突                     ← 仲裁第 8 步产出；无则「暂无」
## 未覆盖的问题（喂料 / 联网补齐方向）
## 已入库条目索引                 ← 一行一条，格式不变，追加在文末
<!-- KB:INDEX:BEGIN -->
<!-- KB:INDEX:END -->
```

规则：
- **索引行格式保持不变**（`- [<id>] <标题> — <一句话摘要> [src:<id>]`），永远追加在**文末**，仍由 `kb.ps1 approve -UpdatePage` 或 agent 手工插入标记之间。
- `## 本类综述` 是**页面级**总览；`### 核心结论` 是**主题级**结论。两者不要混。
- 一个主题写不下（超过约 80 行）→ 拆成两个 `## <主题>`，或把细节留给原文，页面上只留结论与步骤。
- 页面只放「你以后会被问到的东西」；原文永远在 `library/`，需要时用 `[src:<id>]` 点回去。

## 3. 五要素分别落到哪一层

| 内容 | L1 原文 | L2 engram | L3 知识页 |
|---|---|---|---|
| 原文逐字 | ✅ 全文 | ❌ | ❌（可引关键句） |
| 单条命题结论（`<命题>：<结论>。条件：… 来源：… [src:<id>]`） | — | ✅ 一条一个 `engram_save` | ✅ 进 `### 核心结论` |
| 推导 / 步骤 / 边界 / 易错点 | — | ❌（太长，检索不需要） | ✅ 五要素正主 |
| 索引与总览 | — | — | ✅ |

## 4. 消化流程（与五状态审核衔接）

```
1. 收到批准入库的资料（或用户直接提问暴露的知识缺口）
2. agent 读 L1 原文 → 提炼五要素草稿
3. 写提案 _review/queue/<id>.md（按 _templates/review-proposal.md），其中必须含：
   · 将要写入 engram 的条目正文（带 [src:<id>]）
   · 将要更新的知识页 diff（哪个主题、哪个小节、加什么）
   · 五要素自检结果（哪几项齐、哪几项「待补」）
4. 用户批准 → ① L1 落盘 ② engram_save ③ 更新 pages/<大类>.md ④ 提案归档（见 review-workflow.md）
5. 用户驳回 / 要改 → 消化产物一并改，不得先落库
```

**问答时怎么用**：先按 `arbitration.md` 跑完仲裁拿到 `chosen_ids`（含第 4 步正误推理的结论），再用知识页里对应主题的五要素组织答案——**给结论、给推导、给步骤、给边界、给易错点**，全部引用带 `[src:<L1-id>]`。库里没有的主题：明确说「库内未消化」，再询问是否联网补齐或喂料。

## 5. 消化质量自检清单（写提案前逐条过）

1. 术语/符号/单位是否都能读懂（① 齐）？
2. 结论有没有可检验的推导或依据，前提假设写没写（② 齐）？
3. 照步骤能不能真的算出来/做出来（③ 齐）？
4. 有没有写「什么时候不能用」（④ 齐）？
5. 易错点是不是具体到「错在哪、怎么错」（⑤ 齐）？
6. 每个结论是否都带 `[src:<L1-id>]`（无来源不得作结论）？
7. 有没有整段抄原文（违反硬边界 3）？
8. 本主题与已有主题是否重复？重复 → 合并进既有主题，不新开一节。
